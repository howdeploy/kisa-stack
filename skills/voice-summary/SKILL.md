# Voice Summary - Скилл выжимки из голосовых

Создает краткие выжимки из голосовых сообщений и аудиофайлов. Идеален для быстрого понимания содержания подкастов, лекций и длинных записей.

## Режимы работы

### 1. Обработка аудио с выжимкой
**Триггеры:**
- "сделай выжимку из войса"
- "кратко расскажи что в голосовом"
- "суммируй это аудио" 
- "что в этом подкасте"
- "переведи и сделай выжимку"
- "выжми главное из записи"

**Workflow:**
1. Получаю аудиофайл от пользователя
2. Отправляю на транскрипцию через API (Whisper/ElevenLabs)
3. Получаю полный текст транскрипции
4. Сохраняю полную транскрипцию в файл 
5. Создаю развернутую выжимку с 4 блоками:
   - Общий пересказ своими словами
   - Список основных тезисов
   - Мои наблюдения и интерпретации
   - Поиск ссылок на упомянутые проекты/ресурсы
6. Возвращаю структурированную выжимку + ссылку на полный текст

### 2. Только транскрипция (без выжимки)
**Триггеры:**
- "просто транскрибируй"
- "только текст из войса"
- "нужен полный текст"

**Workflow:**
1. Получаю аудиофайл
2. Отправляю на транскрипцию  
3. Возвращаю полный текст без суммаризации

## Технические детали

### API для транскрипции
Использую доступные Speech-to-Text API:
- Автоматический выбор лучшего доступного API
- Поддержка русского и английского языков
- Получение чистого текста без таймкодов

### Формат файлов
**Транскрипция (`.txt`):**
```
[2026-02-01 00:05] Исходный файл: voice_message.opus

полный текст транскрипции...
```

**Выжимка (`.md`):**
```markdown
# Выжимка от 2026-02-01 00:05

## 📖 Общий пересказ
Автор рассказывает своими словами суть контента...

## 📋 Основные тезисы
• Тезис 1 с контекстом
• Тезис 2 с объяснением
• Тезис 3 и его значение

## 🔍 Мои наблюдения
Свободный текст с наблюдениями и интерпретациями. Что автор на самом деле имел в виду, какой глубинный посыл, интересные детали которые можно заметить между строк. Пишу как живой человек, а не списком тезисов.

## 🔗 Упомянутые проекты/ресурсы
- **Название проекта** — описание, [ссылка]()

## Процесс обработки

### Транскрипция + развернутая выжимка
1. Получаю аудиофайл от пользователя
2. **Напрямую обращаюсь к Speech-to-Text API** для транскрипции
3. Сохраняю полный текст в `voice-summaries/transcripts/`
4. **Анализирую текст** и создаю выжимку по 4 блокам:
   - Пересказ своими словами
   - Список основных тезисов  
   - Мои наблюдения и интерпретации
   - **Поиск ссылок** на упомянутые проекты через веб-поиск
5. Сохраняю структурированную выжимку в `voice-summaries/summaries/`
6. Возвращаю полную выжимку + ссылку на транскрипцию

### Только транскрипция
1. Получаю аудиофайл
2. Обращаюсь к API для транскрипции
3. Возвращаю только чистый текст (не сохраняю)

## Уточняющие вопросы

При обработке:
- "Нужна подробная выжимка или краткая?"
- "Сохранить полную транскрипцию?"
- "Это подкаст, лекция или разговор?"

## Action-first режим для голосовых с жалобами/идеями/требованиями

Если пользователь прислал голосовое не ради пересказа, а чтобы **превратить сказанное в артефакт** — например ТЗ, prompt для coding-агента, список правок, требования заказчика — не застревать в длинной аналитической пасте по умолчанию.

Правильный порядок:
1. Вытащить факты, боли, требования и ограничения.
2. Сразу собрать целевой артефакт в нужном формате.
3. Для Telegram и быстрых рабочих чатов по умолчанию делать **краткую, емкую, готовую к вставке версию**.
4. Развернутую версию давать только если ее реально просили.

### Формат по умолчанию для Telegram
- сначала 1 короткая фраза-контекст, если она вообще нужна;
- затем готовый блок: `prompt`, `ТЗ`, `TODO`, `список требований`;
- без огромной подводки, без повторения одного и того же разными словами;
- если пользователь явно просит "кратко/четко/без пасты" — ужимать до 5–12 строк или одного компактного блока.

### Если пользователь присылает несколько войсов с ТЗ/требованиями подряд
Частый рабочий режим: пользователь пересылает голосовые от другого человека не ради пересказа, а чтобы восстановить **что тот хочет как ТЗ**. В этом режиме не начинать каждый войс как новый независимый summary.

Правильный порядок:
1. Держать общий накопительный документ требований в голове текущего диалога.
2. Каждый новый войс обрабатывать как **добавку/уточнение к ТЗ**.
3. Сразу выдавать компактный блок: что добавилось, какие метрики/поля/аналитика/логика теперь нужны.
4. Убирать разговорный мусор, сомнения и повторы, но сохранять числовые ориентиры, названия сущностей и причинно-следственную логику.
5. Если в войсах есть продуктовая аналитика, разделять: цель, текущие показатели, целевые показатели, что вывести в админке, зачем это нужно.

### Если пользователь просит список проблем из нескольких войсов
Это отдельный частый режим: не пересказывать весь разговор, а **собрать короткий баг-лист / список проблем** по нескольким голосовым подряд.

Правильный порядок:
1. Слить все присланные голосовые в один общий набор наблюдений.
2. Убрать повторы и разговорный мусор.
3. Выдать сначала **сухой список проблем** в 3–8 пунктов.
4. Если пользователь потом просит "разверни", раскрывать **те же пункты**, а не переписывать ответ с нуля в другой форме.
5. Если в голосовых описано поведение диалога/воронки, добавлять не только сам баг, но и **как он проявляется в переписке** и **к чему приводит**.

### Два полезных режима для таких войсов
**1. Ультракоротко, для быстрой фиксации**
- только пункты проблем;
- без лишних вступлений;
- хорошо подходит для Telegram и рабочих чатов.

**2. Чуть подробнее, для баг-репорта**
- `проблема`;
- как именно проявляется в диалоге;
- последствие для сценария/конверсии/логики.

### Если пользователь спрашивает, "ты точно все послушала?"
Если у тебя была не прямая аудиообработка, а готовая расшифровка от платформы, отвечать честно и прямо:
- не делать вид, будто слушала ушами;
- сказать, что разобрала **расшифровки всех голосовых**;
- при желании перечислить кратко, что было в 1-м, 2-м, 3-м сообщении.

### Pitfall
- Плохо: после голосового с жалобами на продукт выдать длинный пересказ, а полезный prompt спрятать внизу.
- Плохо: когда пользователь попросил очень короткий список проблем, а ответ расползся в анализ, выводы и советы.
- Плохо: при просьбе "разверни" полностью менять структуру вместо расширения уже собранного списка.
- Хорошо: быстро конвертировать речь в рабочий deliverable, а не в литературное summary.
- Хорошо: сначала дать короткий баг-лист, потом по запросу раскрыть каждый пункт через проявление и последствия.

## Примеры использования

### Выжимка из голосового
**Пользователь:** [присылает 7-минутное голосовое] "сделай выжимку"

**Ответ:** 
```
🎙️ Обработала аудио (7:15)

## 📖 Общий пересказ
Автор делится новогодними размышлениями под алкоголем, рассказывая о двух ключевых ударах 2025 года — болезненном расставании и разочаровании в работе. Несмотря на тяжелые моменты, он нашел свое призвание в работе с контентом и строит планы на четыре новых проекта.

## 📋 Основные тезисы  
• Самые тяжелые события — это не конец, а начало нового этапа
• Призвание — работа с аудиторией и контентом, а не карьерный рост
• Поддержка подписчиков имеет колоссальное значение
• "Просто работать и верить — этого достаточно"

## 🔍 Мои наблюдения
Слушая это голосовое, понимаешь что автор проходит через классическую трансформацию "раненого целителя" — он превращает свою боль в силу для других. Особенно показательно, что он впервые записывает под алкоголем — это не случайность, а способ стать более уязвимым и искренним с аудиторией.

Интересно, как он строит контраст: начинает с самого темного, чтобы подчеркнуть светлые моменты. Главная мысль — внешний успех вторичен перед человеческими связями и внутренним призванием.

## Error Handling

- Файл не найден → "Не могу найти этот аудиофайл"
- API недоступен → "Сервис транскрипции временно недоступен, попробуй позже"  
- Слишком длинный файл → "Файл слишком длинный (>30 мин), разбей на части"
- Поврежденный файл → "Не удается обработать этот аудиофайл"
- Тихий/неразборчивый звук → "Звук слишком тихий или неразборчивый для транскрипции"
- Ошибка выжимки → "Транскрипция готова, но не удалось создать выжимку"
