# Researcher

> **Примечание по инструментам.** Скилл писался в среде Hermes: `web_search` / `web_extract` / `terminal` / `execute_code` / `delegate_task` — её инструменты. В Claude Code / Codex используй аналоги: веб-поиск (Tavily / WebSearch), извлечение страниц (tavily_extract / WebFetch), shell (Bash), субагенты (Agent). Логика скилла от рантайма не зависит.

Короткий и практичный ресёрч без ступора, если один источник поиска умер.

## Основные режимы

### 1. `quick-scan`
Когда нужен быстрый, но нормальный обзор.

Что делать:
- быстро проверить тему через `web_search`
- взять 3–5 сильных источников
- дать короткую выжимку
- оставить достаточно контекста, чтобы потом можно было углубиться без повторного старта с нуля

Когда использовать:
- нужно быстро понять, стоит ли тема внимания
- нужен короткий обзор без перегруза
- нужно подобрать, куда копать дальше

### 2. `deep-research`
Когда нужен уже не обзор, а нормальное погружение.

Что делать:
- собрать несколько качественных источников с разных углов
- сравнить версии, подходы, противоречия
- выделить практические выводы
- сохранить достаточно контекста в ответе, чтобы пользователь мог продолжить разговор с уже собранной базой

Когда использовать:
- нужно реально разобраться в теме
- нужно сравнить инструменты / подходы / мнения
- нужен ресёрч для статьи, дайджеста, решения или стратегии

## Триггеры

Используй естественные фразы, не требуй от пользователя специального синтаксиса.

### Триггеры для quick-scan
- быстро посмотри тему
- дай быстрый ресёрч по ...
- коротко разберись, что там с ...
- глянь, стоит ли вообще в это копать
- быстрый обзор по ...
- собери краткую выжимку по ...

### Триггеры для deep-research
- глубоко исследуй ...
- нормально раскопай тему ...
- собери глубокий ресёрч по ...
- сравни и разберись подробно ...
- хочу разобраться в ... глубже
- сделай полноценный ресёрч по ...

## Выбор режима

Если пользователь явно не назвал режим, выбирай его сама:
- если запрос звучит как быстрый обзор или первичная разведка — `quick-scan`
- если нужно сравнение, решение, подбор workflow, исследование с нескольких сторон или тема явно сложная — `deep-research`

Не заставляй пользователя каждый раз формализовать запрос через двоеточия или служебные метки.

## Ключевой принцип — `signal-only`

Это не отдельный режим, а обязательное правило **для любого поиска**.

Всегда:
- ищи достоверную и полезную информацию
- предпочитай первоисточники и сильные разборы
- отсекай SEO-мусор, маркетинговую шелуху и слабые пересказы
- не тащи в вывод всё подряд только потому, что оно найдено

Если источник сомнительный — помечай это прямо.
Если тема спорная — не опирайся на один источник.

## Базовый принцип работы
Сначала пробуй нативный контур Hermes:
- `web_search`
- `web_extract`

Не считай старые ошибки актуальными автоматически. Если раньше Tavily или другой поиск падал, сначала сделай короткий **живой smoke test сейчас**, а уже потом уходи в фолбэк.

## Рабочий порядок
1. **Smoke test**
   - короткий `web_search`
   - при надобности `web_extract` на 1 URL
2. **Развёртка темы**
   - если тема многослойная, сама разложи её на 2–4 исследовательские ветки
   - сама придумай дополнительные поисковые формулировки и углы атаки
3. **Сбор источников**
   - сделай 2–4 запроса с разных углов
   - отдели сильные источники от мусора
4. **Извлечение сути**
   - читай приоритетные страницы
   - доставай тезисы, цифры, ограничения, практические выводы
5. **Синтез**
   - отвечай коротко
   - но оставляй в ответе достаточно контекста, чтобы потом можно было естественно углубиться в уже проведённый ресёрч

## Когда звать сабагентов
Используй `delegate_task`, если тема реально выигрывает от распараллеливания.

Автоматически зови сабагентов, если одновременно выполняются оба условия:
- тема естественно делится минимум на 2 независимые исследовательские ветки
- каждая ветка даёт отдельную ценность, а не просто дублирует другие

Подходит для случаев вроде:
- нужно исследовать одну тему с нескольких сторон
- нужно подобрать решение для сложного workflow
- нужно сравнить несколько инструментов или подходов
- нужно быстро разделить тему на независимые ветки и исследовать их параллельно

Пример:
Если пользователь ищет решение для ComfyUI workflow, можно самой разбить задачу на ветки вроде:
- готовые workflow и community practices
- ноды и расширения
- performance / VRAM / stability
- альтернативные подходы и trade-offs

Не зови сабагентов, если:
- вопрос маленький и прямой
- можно самой закрыть его за несколько запросов без потери качества
- распараллеливание даст больше шума, чем пользы

То есть темы для отдельных поисковых веток и сабагентов формируешь **ты сама**, если это помогает качеству ресёрча.

## Фолбэк
Если `web_search` / `web_extract` не работают, используй:
- Brave Search HTML через `curl -L -A 'Mozilla/5.0'`
- DuckDuckGo HTML как запасной вариант
- `requests` / `curl` / `execute_code` для чтения и чистки страниц

### Специальный случай: мануалы, PDF и вендорские страницы
- страницы вида `.../manual` у магазинов и брендов часто оказываются бесполезной storefront-обёрткой без самого текста инструкции
- если в поисковой выдаче видно прямую ссылку на PDF/manual asset, лучше сразу идти в неё, а не тратить ходы на витрину магазина
- если `web_extract` не тянет PDF или даёт пустоту, скачай файл через `python3` + `requests` или `curl -L` и попробуй локальное извлечение текста
- порядок предпочтения для локального чтения PDF:
  1. `pdftotext`, если установлен
  2. Python-библиотеки вроде `pypdf` / `PyPDF2`, если доступны
  3. если нормальный парсинг недоступен, используй поисковые сниппеты, alternate manuals mirrors и даже `strings` как грубый последний шанс для поиска коротких сочетаний клавиш, названий режимов и других маркеров
- для железа и клавиатур особенно полезно скрещивать: официальный manual/snippet + Reddit/форумы с практическим подтверждением сочетания клавиш

### Специальный случай: Reddit
- если обычный URL `reddit.com/...` плохо извлекается через `web_extract`, сразу пробуй тот же тред через `https://old.reddit.com/...`
- для текстового чтения и цитирования old.reddit часто вытаскивается гораздо надёжнее обычного Reddit
- если нужен именно живой срез мнений, сочетай `web_search` для поиска тредов и `web_extract` по `old.reddit.com` для чтения содержимого
- если `web_extract` на old.reddit внезапно ругается, будто в URL есть `API key or token`, не делай из этого общий вывод про Reddit: это может быть ложное срабатывание. Практичный порядок такой:
  1. ретрайнуть URL **по одному**, а не пачкой;
  2. попробовать вариант с завершающим `/`;
  3. если один тред всё равно блочится, добрать смысл через `web_search` snippets по exact title и соседние треды, а blocked URL не тащить дальше в пакетный extract.

### Специальный случай: поиск автора / источника по картинке или скриншоту
Когда user присылает арт, мем, скриншот поста или кадр анимации и просит найти автора, не начинай с голых текстовых запросов — сначала выжми из изображения поисковые признаки.

### Специальный случай: перевод текста со стикеров / мемов / маленьких UI-скринов
Когда user просит прочитать и перевести текст с картинки, стикера, скрина пака стикеров или auto-captioned media, сначала отдели **реальные пиксели** от **словесного описания вложения**.

Рабочий порядок:
1. если есть настоящий image attachment / local image path / screenshot — сначала используй vision по самому изображению;
2. если в сообщении есть только auto-описание вида `The user sent a sticker ... It shows: ...`, не выдавай это за OCR и не утверждай точные иероглифы, которых ты не видела;
3. на маленьких сетках стикеров сначала дай честную карту уверенности: что читается точно, что частично, что слишком мыльно;
4. если pack/page не отдаёт сами превью, проси у пользователя скрин конкретного стикера или пачку скринов, а не выдумывай текст по vibe-описанию;
5. когда позже приходит реальный пиксельный стикер, перепроверь прежние догадки и прямо исправь их, не защищая старую версию.

Формат ответа на таких задачах:
- `точный текст`, если реально прочитан с пикселей;
- `похоже, тут ...`, если это только лучшая догадка по размытом изображению;
- отдельно: буквальный перевод и живой русский вариант по смыслу.

Критичный pitfall:
- не путай caption-level description от платформы с фактическим OCR; если нет изображения, можно подтверждать только **смысл описания**, но не точную китайскую/японскую строку.

### Специальный случай: перевод текста со стикеров / мемов / платформенных auto-descriptions
Когда пользователь просит перевести текст с Telegram-стикера, стикерпака, мем-картинки или другого визуального объекта, сначала жёстко отделяй **реальные пиксели изображения** от **платформенного авто-описания**.

Правило:
- если у тебя есть сам стикер, скрин или image attachment, можно делать OCR/vision и называть точный оригинальный текст;
- если у тебя есть только текстовое auto-description вида `The user sent a sticker ... It shows ...`, нельзя выдавать "точный китайский/японский текст" как будто ты его видишь;
- из auto-description допустимо давать только **перевод смысла / вероятный gloss**, явно помечая, что это не посимвольный OCR.

Практический порядок:
1. сначала проверь, есть ли в контексте **реальная картинка**;
2. если картинки нет, но есть только описание стикера, не реконструируй иероглифы по догадке;
3. если раньше ты уже назвала точный текст по описанию, а user просит "проверь ещё раз", признай неопределённость прямо и попроси именно изображение/скрин;
4. формулируй ответ как `по смыслу это ...`, `точный оригинал не вижу без самого изображения`;
5. для паков и мелких сеток не переоценивай OCR по мыльному скрину: лучше пометить плитки как unreadable, чем выдумать текст.

Рабочий порядок:
1. используй vision и выпиши максимально конкретно: персонажи, фандом, поза, стиль, текст на кадре, watermark, возможные теги;
2. затем делай 2 параллельные ветки поиска:
   - обычный web/X поиск по ключевым словам;
   - tag/booru/secondary-source поиск по описанию персонажей и фандома;
3. если находится booru/post mirror/secondary dataset entry, не останавливайся на нём — используй его как мост к alias художника;
4. затем триангулируй alias через вторичные источники, где автора могут упоминать явно: model cards, dataset READMEs, reposts, quote-posts, mirrors;
5. после этого проверяй прямой social handle через X/web_search и только потом называй кандидата;
6. если уверенность неполная, так и помечай; если user подтверждает «да, это он», считай идентификацию закрытой.

Практическая эвристика:
- для anime/furry/game art Danbooru и похожие индексаторы часто лучше обычного веб-поиска как первый alias-bridge;
- Hugging Face / Civitai / dataset/model-card страницы иногда неожиданно содержат прямую привязку alias -> X handle;
- если X плохо извлекается, используй search snippets и зеркала как подтверждающий слой, а не единственный источник истины.

### Специальный случай: большие doc-страницы с anchor-секциями


Рабочий порядок:
1. сначала используй vision, чтобы вытащить **поисковые признаки**: персонажи, фандом, цвет/паттерн (например calico), поза, наличие текста, watermark, стиль, возможные теги;
2. затем делай **несколько узких web_search-запросов** по этим признакам, а не один общий;
3. если это фанарт/анимация, ищи не только прямой пост автора, но и **репосты, агрегаторы, Danbooru/Gelbooru, HuggingFace/LoRA pages, repost accounts**, где часто всплывает alias автора;
4. если обычный поиск не даёт прямого автора, ищи **alias bridge**: booru-artist-name -> Pixiv/X handle -> профиль;
5. если X/Twitter плохо извлекается, используй то, что видно в поисковых сниппетах: они часто уже показывают **handle, display name, текст поста и дату**, чего хватает для атрибуции даже без полноценного extract;
6. после нахождения кандидата проверь его **по стилю и серии работ**: ищи соседние посты с тем же фандомом/персонажами, а не хватай первый совпавший handle.

Полезные эвристики:
- booru-страницы часто содержат строку `drawn by <alias>` — это отличный pivot;
- HuggingFace / LoRA README иногда прямо указывает `artist on X: @handle` и может связать obscure alias с живым профилем;
- X search results по exact phrase из сниппета (`"Minecraft cat"`, название серии и т.п.) часто приводят к оригинальному посту даже без логина.

Подача ответа:
- если уверенность не 100%, говори `похоже, это ...` и коротко объясни цепочку атрибуции;
- если найден не точный твит, а профиль автора — отдай профиль и предложи отдельно добить именно исходный пост/анимацию.

### Специальный случай: Telegram sticker pack / addstickers link
Когда пользователь кидает ссылку вида `https://t.me/addstickers/<set>` и просит **посмотреть все стикеры / перевести текст на картинках / понять, что там написано**, не делай вид, что содержимое уже доступно из обычного HTML.

Рабочий порядок:
1. сначала проверь сам `addstickers` URL через обычный extract/fetch — иногда там есть хоть базовый метадатный след;
2. затем попробуй найти **публичное зеркало / каталог / индекс** по shortname пака и exact URL;
3. если зеркала с превью нет, честно считай, что у тебя **нет самих изображений**, даже если landing page открывается;
4. в таком случае не выдумывай перевод и не обещай «посмотреть все картинки» без доступа к картинкам — прямо попроси пользователя прислать **скриншоты, сами стикеры или пересланные изображения**;
5. как только изображения даны напрямую, переходи из режима ресёрча в vision/OCR-задачу: вытаскивай текст, помечай нечитабельные места, различай буквальный перевод и перевод по смыслу.

Практическая эвристика:
- Telegram `addstickers` страница часто отдаёт только оболочку `Add Stickers`, без списка стикеров и без прямых image URLs;
- отсутствие превью в публичном веб-контуре — это не «в паке нет текста», а просто отсутствие доступа к самим картинкам;
- в ответе пользователю лучше сразу дать **самый короткий путь к результату**: «пришли скрины/стикеры сюда, и я переведу всё точно».

### Специальный случай: большие doc-страницы с anchor-секциями
- страницы документации вида `.../docs#section` или длинные feature-overview страницы часто плохо подходят для прямого `web_extract`: он может вернуть общий пересказ всей страницы, потерять нужный якорный блок или обрезать контент ради context management
- если пользователю нужна выжимка именно по одной секции, сначала попробуй `web_extract`, но сразу проверяй: действительно ли в результате есть нужный anchor-блок, а не только page-wide summary
- если extract слишком общий или обрезанный, переключайся на текстовый фолбэк: `python3` + `requests` и достань HTML страницы локально
- для таких страниц часто достаточно лёгкого парсинга без внешних библиотек: найти `name="anchor"` / `href="#anchor"`, вытащить соседний `<h3>/<h4>` блок и очистить HTML через `re`/`html.unescape`
- если тема разбита на соседние подзаголовки, полезно вытащить не только целевой anchor, но и ближайшие subsections после него — так легче собрать краткую, но точную выжимку без лишнего шума
- не фиксируйся на одной секции, если user спрашивает про «все новые функции» на странице: сначала быстро картируй список заголовков, потом уже собирай выжимку по новым/релевантным блокам

Если браузер недоступен или страница тяжёлая, не трать время на упрямство — переключайся на текстовый контур.

## Формат ответа
По умолчанию отвечай **коротко и по сути**, без раздутого отчёта.

По умолчанию предпочитай **paragraph-first** подачу: сначала один живой абзац с главным выводом, а уже потом — только если реально нужно — короткие пункты. Не дублируй ответ "короткой версией" после полной версии и не превращай выжимку в GPT-отчёт.

### Специальный случай: ресёрч нужен как сырьё для сценария, озвучки или короткого talking-points блока
Если пользователь просит выжимку **для ролика, записи, сценария, озвучки** или прямо просит **«ужми до короткого списка советов»**, не держись за paragraph-first любой ценой. В этом режиме полезнее:
- дать **4–8 очень коротких буллетов**;
- формулировать их как **советы / наблюдения / тезисы для проговаривания**, а не как аналитический мини-отчёт;
- не расписывать каждый пункт, если пользователь не просил;
- если потом он спрашивает про один конкретный буллет, объяснить его **отдельно и кратко**, одним плотным абзацем.

Иными словами: для обычного ресёрча — живой абзац сначала; для сценарного squeeze-формата — сразу компактный список без воды.

Хороший базовый формат:


### Специальный случай: user прислал ссылки на настройки / features / опции продукта
Когда задача звучит как «изучи эти ссылки и скажи, что тут реально полезно мне», не ограничивайся перечислением названий опций.

### Специальный случай: вопрос про capability-границы — что умеет платформа, что умеет локальная интеграция, и можно ли это «дописать скиллом»
Когда пользователь спрашивает в духе **«умеет ли это Telegram / API / Hermes / можно ли сделать skill»**, не смешивай 4 разных слоя в один ответ:

1. **upstream platform/API** — что вообще позволяет внешний API;
2. **SDK/library layer** — есть ли уже готовые методы/типы в используемой библиотеке;
3. **local product integration** — прокинута ли эта возможность в текущем продукте/репозитории/адаптере;
4. **agent skill vs tool boundary** — может ли это быть просто skill, или нужен новый tool / gateway patch / MCP server.

Рабочий порядок:
1. сначала проверь **локальную интеграцию**: docs, gateway/adapter code, существующие tool entrypoints;
2. отдельно проверь **установленный SDK** живым introspection / grep по venv, чтобы не гадать «поддерживает библиотека или нет»;
3. отдельно проверь **upstream API/docs/changelog**;
4. в выводе жёстко раздели:
   - `API умеет`;
   - `локальный Hermes сейчас не экспонирует`;
   - `skill alone недостаточен` или `достаточен`, в зависимости от слоя;
5. если feature требует **нового типа сообщения, нового transport primitive, callback handling, auth path или persistent external state**, по умолчанию считай, что **одного skill недостаточно** — нужен tool / MCP / plugin / gateway patch;
6. если feature можно собрать из уже существующих tools и side effects не требуют нового transport primitive, тогда skill действительно может быть достаточной оболочкой.

Практическая эвристика:
- **skills — это инструкции и workflow**, а не магическое расширение транспортного слоя;
- skill может научить пользоваться уже существующим tool, terminal, execute_code или MCP tool;
- skill **не добавляет сам по себе** в Telegram новый message type, в Hermes новый gateway capability или в Bot API новый endpoint;
- если local adapter уже умеет соседние primitives (например, inline buttons), это важно прямо назвать: возможно, лучший practical путь — собрать UX на них, а не ждать идеального нативного feature.

Подача ответа на такие вопросы:
- начинай с одного прямого вывода: `да, API умеет, но Hermes сейчас это не вывел`, `нет, локально это ещё не подключено`, `да, это можно сделать, но не одним skill`;
- затем коротко разведи слои `API / SDK / local integration / skill boundary`;
- в конце дай **2–3 реалистичных implementation paths** с trade-offs.

Если по теме есть собранные сессионные заметки, добавь короткую ссылку на `references/telegram-checklists-capability-layering.md` или другой релевантный reference-файл.

Минимальный синтез должен отвечать на 3 вопроса:
1. **что это делает простыми словами**;
2. **какой практический эффект в быту**;
3. **кому это реально нужно, а кому можно не трогать**.

Хороший паттерн ответа:
- сначала коротко отдели **официальный reference** от **community/inspiration-источников**;
- затем сгруппируй опции по смыслу: workflow/UX, shell integration, visual/cosmetic, remote/SSH, tooling и т.п.;
- для каждой реально важной опции дай не сухое имя, а объяснение человеческим языком: «это глубина истории терминала», «это выпадающий quick terminal», «это автокопирование при выделении»;
- в конце дай прямой вывод уровня `скорее да / спорно / больше игрушка`, особенно если пользователь уже чем-то пользуется и просит понять, нужно ли ему это.

Если вопрос упирается в **user-facing capability**, а официальный reference плохо показывает UX-слой, добери ответ через **GitHub issues/discussions/release notes**: они часто подтверждают, существует ли уже реальная команда, пункт меню, command-palette action или keybind action.

Но тут важно не перепутать два разных уровня:
- наличие команды / метаданных / rename-action под капотом;
- наличие постоянного видимого UI-элемента на экране.

Например, `prompt_surface_title` может существовать как action для именования split, но это ещё не значит, что Ghostty рисует постоянную плашку/label на divider каждого split. Не повышай «rename action exists» до «visible split title bar exists», пока источник явно не показывает сам UI.

Если тема про **визуальные кастомизации** вроде шейдеров, тем или эффектов, не останавливайся на голом списке GitHub-реп. Отдельно ищи **showcase-источники**: статьи, скриншоты, GIF/видео, сравнения комбинаций. Пользователю часто нужно не «какие репы существуют», а **где быстро глазами понять, как это выглядит**.

На таких задачах цель — не инвентаризация всех флагов, а помощь в решении «ставить или не ставить».

## Качество
- не доверяй одному источнику на спорных темах
- не тащи SEO-мусор в вывод
- если вывод зависит от текущего состояния инструмента или сервиса, перепроверь это живым тестом
- если нашла хороший operational insight, обнови соответствующий skill
- отвечай так, чтобы исследование можно было продолжить дальше без ощущения, что каждый раз нужно начинать заново

### Специальный случай: scam / rug / founder-controversy вокруг продукта
Когда пользователь просит раскопать **скам, rug pull, founder controversy, бойкот продукта из-за поведения автора** или историю вида «фаундер токена/проекта украл деньги, можно ли теперь пользоваться продуктом», не смешивай в одну кучу **моральную драму, продуктовый риск и on-chain claims**.

Минимальный порядок такой:
1. сначала **раздели сущности**: продукт / репозиторий / npm-пакеты / токен / фаундер / экосистема, где всё это раскручивалось;
2. отдельно проверь **прямые технические артефакты** по продукту: GitHub README, pinned discussions, issues, releases, npm registry metadata, maintainer names, modified timestamps, package rename/migration notices;
3. отдельно проверь **скандальную ветку**: X-посты, Reddit, экосистемные медиа, вторичные summaries;
4. в выводе **жёстко разделяй**:
   - что подтверждено напрямую репозиторием / registry / docs;
   - что подтверждено сильными вторичными источниками;
   - что остаётся allegation без независимого forensic proof;
5. если вопрос пользователя по сути про «отказываться ли от продукта», закончи ответ **практическим trust/supply-chain выводом**, а не только пересказом драмы.

Что почти всегда полезно проверить:
- есть ли community fork / migration path;
- есть ли официальный notice о переезде репозитория;
- висят ли старые npm-пакеты под прежним контролем;
- найден ли malware / exfiltration payload или риск именно в ownership/trust layer;
- есть ли нейтральный on-chain forensic разбор с wallet attribution и tx hashes, или сумма ущерба гуляет только по пересказам.

Практическая эвристика:
- если форк/комьюнити пишет «код чистый, но старые package names под старым publisher control», не упрощай это до «malware найден»;
- если в X все повторяют сумму вроде `$500K`, но ты не нашла первичный forensic source, так и пиши: **сильное allegation, но не жёстко подтверждённая сумма**;
- если один и тот же бренд одновременно означает **tool + token**, всегда явно отделяй **можно ли пользоваться кодом** от вопроса **был ли rug по токену**.

### Специальный случай: security incident / compromise / "взломали ли X"
Когда пользователь спрашивает про **взлом сервиса, аккаунта, GitHub/org, npm/PyPI ecosystem, OAuth compromise, CI/CD compromise или supply-chain incident**, не отвечай как на обычную новость.

Минимальный порядок такой:
1. сначала отдели **компрометацию самой платформы** от компрометации **аккаунта / токена / OAuth app / CI workflow / third-party integrator / package maintainer**;
2. проверь **официальный источник** вендора: docs, blog, incident post, advisory, changelog, status;
3. добавь хотя бы один **технический разбор / postmortem / strong secondary source**, если тема уже активно расследована;
4. если пользователь пытается понять, затронуло ли это его, закончи ответ **практическим triage checklist**: что проверить в UI, в логах, в lockfiles, в токенах, в почте.

#### Если первоисточник — тред в X / Twitter
Это частый и неприятный кейс: `web_extract` по `x.com` часто даёт пустоту или ошибку. Не стопорись на этом.

Рабочий порядок:
1. попробуй прямой `web_extract` по `x.com`;
2. если пусто/ошибка — сразу ищи **зеркало** (`xcancel.com`, Thread Reader и т.п.) или поисковый сниппет с цитатой начала треда;
3. добери подтверждение через **secondary sources**, которые уже процитировали тред целиком или кусками (HN summary, BleepingComputer, The Hacker News, LinkedIn-перепост с видимым текстом, vendor-adjacent coverage);
4. в ответе **чётко разделяй**, что подтверждено самим вендором в треде, а что пришло из вторичных разборов;
5. если follow-up посты треда недоступны напрямую, не выдумывай их: опирайся только на цитируемые фрагменты из сильных вторичных источников.

Для incident-разборов по X-тредам особенно важно не смешивать:
- первый официальный statement (`investigating`, `no evidence`, `monitoring`);
- follow-up детали (`initial access`, `scope`, `containment`, `secret rotation`);
- claims атакующего;
- интерпретации журналистов и исследователей.

На таких темах особенно важно не склеивать в одну кучу разные классы риска. Формулировка вроде «GitHub взломали» часто распадается на совсем разные сценарии:
- компрометирован GitHub account;
- украден OAuth token / PAT / session;
- скомпрометирован сторонний интегратор;
- злоупотребили GitHub Actions / OIDC / workflow trust boundary;
- заражён npm/PyPI пакет и через него украли GitHub credentials.

### Как отвечать на такой вопрос
Если пользователь спрашивает по сути: «это актуально?», «есть ли риск?», «меня это касается?», начни с одного прямого вывода в первой строке:
- `Да, это актуальный класс риска.`
- `Нет, прямого подтверждения по этой штуке я не нашла.`
- `Скорее это не взлом GitHub как платформы, а компрометация токенов / CI / пакетов.`

Только потом давай контекст и **короткий список проверок**.

### Что почти всегда полезно включить в triage
- review authorized OAuth apps / integrations;
- review PATs / token scope / revocation state;
- org audit log с датным фильтром;
- members / outside collaborators;
- suspicious GitHub Actions runs, branches, workflow edits;
- lockfiles / dependency versions, если речь о supply-chain инциденте;
- notification inbox / phishing indicators, если есть шанс account takeover.

### Специальный случай: локальная коммунальная авария / отключение воды, света, отопления
Когда пользователь просит раскопать, **почему в конкретном городе/районе пропала вода, свет, отопление или связь**, не ограничивайся общими новостями по региону. У таких событий часто слабая федеральная видимость и запаздывающая официальная коммуникация.

Рабочий порядок:
1. сначала проверь **локальные СМИ / городские паблики / Telegram snippets** по точному городу и типу проблемы;
2. отдельно проверь **официальный контур**: сайт/соцсети местной администрации, ресурсоснабжающей организации, теплосети, водоканала, электросетей;
3. если свежего официального поста нет, ищи **очень недавние аналогичные инциденты** в том же городе за последние дни: это помогает понять, похоже ли происходящее на каскадную аварию, а не на единичный дом;
4. обязательно **разделяй плановое и аварийное**: плановое отключение горячей воды не объясняет пропажу холодной воды, а одновременное отсутствие ХВС+ГВС чаще указывает на внештатный сбой, электропитание ЦТП/котельной или крупную коммунальную аварию;
5. в ответе прямо помечай уровень уверенности: `официально подтверждено`, `подтверждается локальными медиа`, `выглядит вероятно, но свежего официального подтверждения не нашла`;
6. если пользователь, скорее всего, хочет действовать, а не читать длинный разбор — обязательно дай **операционные контакты**: диспетчерская, горячая линия, аварийная служба, глава округа/ЕДДС, если нашлись в надёжном источнике.

Практические эвристики:
- snippets из `t.me/s/...` и локальных СМИ часто дают больше сигнала, чем федеральные новости;
- если найдён только график плановых отключений ГВС, не делай из этого вывод про полное отсутствие воды без отдельного подтверждения по ХВС;
- отсутствие свежей официальной публикации **не равно** отсутствию аварии — в локальном ЖКХ-контуре это обычная история; просто формулируй это честно;
- полезный формат вывода: 1 абзац с прямым выводом + 2–4 коротких действия/контакта.

### Специальный случай: feasibility ресёрч по обучению/дообучению модели на конкретной GPU
Когда пользователь спрашивает в духе **«потянет ли GPU X обучение модели Y»**, **«смогу ли я обучить LoRA на арендованной карте»**, **«что на этом железе реально делать»**, не отвечай общими словами про TFLOPS и «должно хватить». Для таких задач нужен отдельный practical split.

Рабочий порядок:
1. сначала отдели **тип обучения**: LoRA / full finetune / DreamBooth / ControlNet / inference-only — это важнее голой модели GPU;
2. затем проверь **архитектуру самой модели**, а не только бренд/чекпоинт: SD1.5-style U-Net, SDXL, DiT, FLUX-like, кастомный text encoder / VAE / adapter stack;
3. добери **официальный training path**: model card, upstream training docs, repo docs, supported scripts/entrypoints;
4. отдельно ищи **community VRAM reports** и practical configs: batch size, resolution, precision, checkpointing, cache flags, known NaN/fp16/bf16 caveats;
5. отдельно проверь **экономику аренды**: хотя бы один живой pricing source, и посчитай rough cost for 4/8/12h через tool, не в уме;
6. в выводе жёстко раздели:
   - `потянет LoRA`;
   - `потянет с компромиссами`;
   - `full finetune уже мимо`;
   - `лучше сменить базовую модель под задачу`, если user хочет реализм на anime-base или наоборот.

Практические эвристики:
- одинаковый объём VRAM **не означает** одинаковую практическую скорость: для diffusion training отдельно смотри bandwidth / архитектуру / memory-saving flags;
- для exotic/open model stacks часто главный вопрос не «сколько GB», а **есть ли официальный script и какие нужны дополнительные веса** (text encoder, adapter, VAE, tokenizer);
- Hugging Face **discussions** и issue threads по training support часто важнее общих блогов: там всплывают реальные VRAM numbers, NaN caveats и working learning rates;
- если модель заведомо не под целевой домен (например anime illustration base для photoreal identity training), это нужно сказать прямо, а не делать вид, что всё решится LoRA.

Подача ответа:
- начинай с одного практического вывода: `да, для LoRA нормально`, `да, но только с 512/768 и batch 1`, `нет, full finetune на этой карте уже нерационален`;
- затем коротко разведи **capability / constraints / best use cases / not recommended use cases / rough cost**;
- если нашла много полезных цифр и ссылок, имеет смысл вынести их в `references/` как condensed knowledge bank для похожих будущих задач.
- для feasibility-вопросов по diffusion / LoRA на конкретной GPU см. `references/anima-lora-feasibility.md` как образец хорошего condensed knowledge bank: там полезный паттерн — отдельно фиксировать архитектуру модели, официальный training path, community VRAM numbers, rough rent-cost framing и границу `LoRA ok / full finetune уже нет`.

### Специальный случай: policy / pricing / billing / ToS у вендора
Когда пользователь спрашивает не просто «что умеет продукт», а как **тарифицируется**, **что входит в подписку**, **что считается API usage**, **что разрешено policy/ToS**, не опирайся на один слой документации.

Минимум проверь 3 слоя, если они существуют:
1. официальные product/docs страницы
2. help center / support статьи
3. pricing страницы / usage docs

Почему это важно:
- продуктовые docs часто объясняют механику, но не consumer billing
- pricing говорит цену, но не всегда говорит policy-границы
- help center часто содержит критичные practical-оговорки вроде «если выставлен API key, биллинг пойдёт как API, а не как подписка»

На таких вопросах отдельно различай:
- **контур аутентификации / биллинга**: подписка, OAuth, API key, PAYG, extra usage
- **архитектурную механику**: local tool, MCP, SDK, external tool, web/tool call

Не смешивай их. Частая ловушка: пользователь спрашивает «считается ли external tool отдельным платным вызовом», а правильный ответ упирается не в tool semantics, а в **каким контуром идёт auth и по каким terms работает сценарий**.

### Как отвечать на прямой вопрос о деньгах / policy
Если пользователь спрашивает в лоб: «это входит в подписку или платится отдельно?», «можно или нельзя?», «safe или risky?», **начни ответ с одного прямого вывода в первой строке**.

Хороший паттерн:
- `Да, это оплачивается отдельно.`
- `Нет, это входит в обычную подписку.`
- `Да, можно, но только через API key.`
- `Нет, по consumer path это не тот контур.`

Только **после** этого давай нюансы: credit bucket, extra usage, серые зоны policy, отличия SDK от CLI wrapper, и так далее.

Не начинай такие ответы с длинной развилки, истории вопроса или осторожного «картина сложнее». Сначала бинарный вывод, потом объяснение. Если есть неопределённость, она должна уточнять вывод, а не заменять его.

Если ресёрч про Claude Code / Agent SDK / Anthropic policy, см. также `references/anthropic-claude-code-policy-billing.md`.
Если ресёрч про GitHub compromise / OAuth tokens / Actions abuse / supply-chain around GitHub, см. `references/github-compromise-triage.md`.
Если ресёрч про Telegram bot-to-bot delivery / loop prevention / BotFather mode, см. `references/telegram-bot-to-bot-communication.md`.
Если ресёрч про GSD / Get Shit Done controversy, rug-pull allegations и migration risk, см. `references/gsd-rug-sources.md`.
